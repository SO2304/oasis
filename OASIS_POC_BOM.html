0. À quoi sert ce banc et comment je le supervise

Ce POC matérialise une seule tranche d'OASIS : le nœud LoRa-mesh (pas la face drone/PX4, pas le daemon téléphone). L'objectif est de sortir du « logiciel vert » et de répondre à la seule question qui compte : est-ce que le driver SX1262 que nous venons d'écrire parle réellement à la puce, émet un paquet signé, et un autre nœud le reçoit puis le vérifie ?

Modèle de supervision. Les 3 nœuds sont alimentés et lus par le PC via USB. Chaque Pico apparaît comme un port série (COM sous Windows). Le firmware de chaque nœud écrit ses traces sur ce port (init radio, TX, RX, vérif de signature, airtime, dédup). Côté PC, un moniteur série redirige chaque flux vers un fichier journal (node_A.log, node_B.log, node_C.log). Je lis ces fichiers pour diagnostiquer, corriger le firmware/driver, et te guider à chaque étape — c'est la boucle « monitor → corriger → superviser ».

Honnêteté (lis-moi avant d'acheter). Cette liste couvre le matériel. Le firmware de nœud qui fait tourner le driver + la mesh + écrit les traces USB n'est pas encore écrit (voir §8). Acheter ces pièces ≠ test prêt à lancer. De plus, deux détails du driver doivent être confirmés/complétés selon le module choisi (oscillateur TCXO, commutateur RF) — voir §7. Je signale tout, rien n'est caché.

4. Côté PC — monitoring et supervision

C'est ce qui me permet de « voir » le banc et de corriger.

  1. Branchement. Hub alimenté → PC ; les 3 Picos → hub. Au flash, chaque Pico apparaît comme un volume USB (mode BOOTSEL) ; en fonctionnement, comme un port série COM (USB CDC).
  2. Identification. Note quel COM = quel nœud (Gestionnaire de périphériques → Ports COM). Étiquette physiquement A/B/C.
  3. Journalisation. Un moniteur série par nœud, redirigé vers un fichier que je lis :
    pio device monitor -p COM5 -b 115200 | Tee-Object node_A.log
    (ou un court script pyserial). 115200 bauds, 8N1.
  4. Ce que le firmware émet (à implémenter, §8) : init radio OK/KO, fréquence/SF/BW appliqués, chaque TX (taille, airtime µs, budget duty-cycle restant), chaque RX (RSSI/SNR, octets), résultat process() mesh (ARRIVED / Drop+raison), rejets de signature v0A, compteurs Bloom.
  5. Boucle de supervision. Tu me partages les node_*.log ; je diagnostique (ex. « init renvoie Driver(\"busy pin\") → BUSY mal câblé ou TCXO non configuré »), je corrige le firmware/driver, on reflashe, on relit.

6. Sécurité et pièges classiques

Jamais d'émission sans antenne. Émettre sans antenne (ou sans charge 50 Ω) renvoie la puissance dans l'étage PA du SX1262 et peut l'endommager. Visse l'antenne avant la première mise sous tension et ne la retire jamais tant qu'un nœud peut émettre.
  • Câble « charge seule ». Le piège n°1 : aucun port COM n'apparaît. Utilise des câbles micro-USB données.
  • Masse commune. Pico et SX1262 doivent partager le GND (déjà via le fil noir) ; pas d'alimentation séparée flottante.
  • 3,3 V strict pour la radio (cf. §3).
  • Réglementaire EU868. Reste à 868 MHz, ≤ 14 dBm (25 mW PIRE) et respecte le duty-cycle 1 % — c'est déjà ce que calcule/limite le module airtime/DutyCycleThrottler côté logiciel.
  • ESD. Touche une masse / porte le bracelet avant de manipuler les cartes.

7. Notes de compatibilité (issues du driver que j'ai écrit)

Deux détails matériels conditionnent le bon fonctionnement avec le driver actuel. Je les expose car ils orientent le choix du module (article #2).

7.1 Oscillateur : XTAL vs TCXO — point d'attention

Beaucoup de modules SX1262 embarquent un TCXO alimenté/piloté via DIO3. Dans ce cas, l'init doit appeler SetDIO3AsTcxoCtrl (tension + délai de stabilisation) avant la calibration, sinon la PLL ne verrouille pas et la radio ne démarre pas. Le driver actuel ne le fait pas encore. Conséquence :

  • Module à quartz (XTAL) → fonctionne avec le driver tel quel. À privilégier pour le premier test.
  • Module à TCXO → il faudra ajouter SetDIO3AsTcxoCtrl au driver (petite tâche firmware, ~10 lignes). Je la ferai pendant la bring-up si tu prends un module TCXO.

7.2 Commutateur RF : interne (DIO2) vs externe (TXEN/RXEN)

Le driver suppose le commutateur RF interne du SX1262 (piloté par DIO2, schéma de référence Semtech). Certains modules (ex. Ebyte E22) exposent des broches TXEN/RXEN externes : ils demandent 2 GPIO de plus et du code de pilotage du commutateur, non présent dans le driver. Choisis un module à commutateur interne DIO2 pour rester aligné avec le driver et le brochage à 9 fils du §3.

En résumé pour l'achat (article #2) : SX1262 · 868 MHz · SPI · 3,3 V · headers 2,54 mm · commutateur RF interne (DIO2) · de préférence XTAL (sinon je complète le driver pour le TCXO) · connecteur SMA (ou IPEX + pigtail).

8. Ce qui n'est PAS dans cette liste (à produire avant le test)

Le matériel ne suffit pas. Pour lancer le POC supervisé, il manque — côté logiciel, gratuit :

  1. Le firmware de nœud (le vrai chaînon manquant) : un binaire no_std RP2040 qui (a) instancie le driver Sx1262Driver avec un HAL embedded-hal 1.0 (ex. rp-hal/embassy-rp), (b) fait tourner la mesh (MeshRouter v0A), (c) écrit les traces sur l'USB série. Il n'existe pas encore : oasis-mcu-demo utilise embedded-hal 0.2.7 et n'importe pas le driver. C'est la prochaine tâche logicielle.
  2. Compléments driver éventuels : SetDIO3AsTcxoCtrl (si module TCXO), pilotage TXEN/RXEN (si commutateur externe) — cf. §7.
  3. Chaîne d'outils PC : rustup + cible thumbv6m-none-eabi + elf2uf2-rs ou probe-rs + un moniteur série. Gratuit, pas un achat.
Ordre conseillé. 1) Commander le matériel (cette liste). 2) Pendant la livraison, j'écris le firmware de nœud + complète le driver si besoin. 3) À réception : montage §3, vérif multimètre, jalons M1→M2→M3 avec monitoring §4. Tu m'envoies les journaux, je corrige en boucle.

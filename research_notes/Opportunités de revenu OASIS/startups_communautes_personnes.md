That "evidence of intervention" duty is the direct regulatory hook for OASIS's relay-enforced revocation + persisted counter window + intervention log.

### Inferences
- ARX Robotics is the single most actionable target: it has three open roles whose scope (platform security, IEC 62443, CRA, certification to "military and European standards") maps exactly onto a signed-command / secure-boot / revocation stack. Approach: respond to the Safety & Security Platform or Senior Cybersecurity Engineer requisitions with a technical note on OASIS v0B (payload-bound signature, persisted counter window, relay-enforced revocation, RP2040 silicon evidence) rather than a sales email.
- The defence tier (Quantum Systems, Helsing, Stark, Tytan, Frankenburg) has cash but tends to build in-house; the realistic angle is a supplier/subcontract conversation about an auditable, formally-verified actuation gate (Kani proofs + silicon reports) rather than a full stack replacement.
- For the agri/industrial tier, the 20 Jan 2027 deadline makes the "evidence of intervention" and "protection against corruption" duties a compliance cost; Agreenculture, Nature Robots, FarmDroid and Movu have fresh budgets and sell autonomy *kits* to OEMs, so a drop-in authority component is a plausible fit. Movu's "Robotics Safety Engineer" vacancy is a direct entry point.
- Retrofit providers (AgXeed-type VCU retrofits, Agreenculture kits) carry Article 18 manufacturer liability, which strengthens the case for a documented command-authentication layer.

## Key Question 2 — Open-source communities and threads where unauthenticated/replayable relayed commands and intervention logging are being discussed in 2026

### Takeaway
The problem OASIS v0B addresses is live in at least four codebases this quarter: PX4 (CVE-2026-1579 published 31 Mar 2026; PRs #28697/#28698 on the shared signing replay table, opened 15 Sep 2026; PR #29004 on persisted timestamp checkpoints, opened 6 Oct 2026 — all open), Meshtastic 2.8 (XEdDSA signing merged 13 Jun 2026; relay-rewrites-signed-payload bug fixed 6 Oct 2026; anti-spam trust ladder PR closed unmerged), CIRISServer (#402 "signed fabric requests bind neither target nor freshness", open since 14 Aug 2026, awaiting a headers-vs-body decision), and Modbus stacks (libmodbus #874 unauthenticated DoS, nanoMODBUS #122 unauthenticated OOB write, both open). The Victron "MODBUS restriction" request and the ArduPilot GPS-spoofing timestamp issue show the same gap from the user and flight-controller sides.

### Cited Findings

**PX4 / MAVLink**
- CVE-2026-1579 — CWE-306, published 31 Mar 2026, assigner ICS-CERT (CISA advisory ICSA-26-090-02); when MAVLink 2.0 signing is not enabled, any message including SERIAL_CONTROL (shell access) can be sent by an unauthenticated party; CVSS v4 9.3 / v3 9.8; reported by Dolev Aviv (Cyviation); signing is off by default — [MITRE CVE record](https://cveawg.mitre.org/api/cve/CVE-2026-1579); [Lutra Security fieldguide](https://fieldguide.lutrasecurity.com/CVE-2026-1579); [INCIBE-CERT](https://www.incibe.es/en/incibe-cert/early-warning/vulnerabilities/cve-2026-1579); [Security Arsenal hardening guide](https://securityarsenal.com/blog/cve-2026-1579-px4-autopilot-remote-command-execution-detection-and-hardening-guide); [Aviatrix threat research](https://aviatrix.ai/threat-research-center/px4-autopilot-2026-mavlink-vulnerability).
- PX4 PR #28697 "fix(mavlink): lock the shared signing stream table while parsing" — author julianoes, opened 15 Sep 2026, OPEN, approved by dakejahl 16 Sep 2026; receivers on different links race on the shared signing replay table, so a replayed message on a second link could be accepted; affects v1.18.0-alpha1+; reported privately by lihnucs; backport to release/1.18 planned — [GitHub](https://github.com/PX4/PX4-Autopilot/pull/28697).
- PX4 PR #28698 "fix(mavlink): change signing state under the send lock" — julianoes, opened 15 Sep 2026, DRAFT, stacked on #28697; SETUP_SIGNING or key reload can tear the signing key/timestamp used by the sender, and the timestamp written to the key file can be torn — [GitHub](https://github.com/PX4/PX4-Autopilot/pull/28698).
- PX4 PR #29004 "fix(mavlink): persist signing timestamp checkpoints" — author ibondarenko1, opened 6 Oct 2026, OPEN, no reviews; signing does not checkpoint the advancing timestamp so a restart loads stale state; proposes 60 s checkpoints, max(stored, live, system clock) on reload, atomic key-file writes; author states this is "not a guarantee of complete replay prevention across restart" and NuttX/hardware/power-loss not validated; flash +1.7–1.9 KB; px4_fmu-v2 at 99.09 % flash — [GitHub](https://github.com/PX4/PX4-Autopilot/pull/29004).
- PX4 issue #26813 "[Bug] Protect against MAVLink signing silently failing" — hamishwillee, opened 18 Mar 2026, CLOSED 16 Apr 2026 via PR #26894 which removed MAV_SIGN_CFG so signing is controlled only by the key; the request for user feedback on key-setting success was not addressed — [GitHub](https://github.com/PX4/PX4-Autopilot/issues/26813).
- QGroundControl issue #14160 "PX4 Mavlink Signing Issues" — DonLakeFlyer, opened 18 Mar 2026, closed 20 Mar 2026 via PR #14169 (milestone V5.1); asks for co-located setup/enable, per-vehicle password storage, visible signing status, and an ACK for SETUP_SIGNING (no way to confirm it worked) — [GitHub](https://github.com/mavlink/qgroundcontrol/issues/14160).
- ArduPilot issue #13860 "MAVLink 2.0 message signing can be broken under GPS spoofing" — KimHyungSub, opened 22 Mar 2020, closed 26 Mar 2020 by peterbarker; GPS spoofing before first GPS fix can set the signing timestamp back (clock starts at 1970) enabling replay; maintainers said the key must be set up over a secure channel and asked for a reproducible case — [GitHub](https://github.com/ArduPilot/ardupilot/issues/13860).

**Meshtastic (LoRa mesh)**
- PR #10478 "Packet Signing via XEdDSA" — jp-bennett, opened 14 May 2026, merged 13 Jun 2026 into develop; signature covers [fromNode | packetId | portnum | payload]; blocks replay-with-changed-ID, reattribution, port redirection; unsigned packets from previously-signing nodes rejected; follow-up #10534 refined unsigned-packet rejection; no explicit duplicate cache/timestamp for byte-identical resends described — [GitHub](https://github.com/meshtastic/firmware/pull/10478); background on 256-byte LoRa limit — [Meshtastic docs](https://meshtastic.org/docs/about/overview/encryption/limitations/).

### Inferences
- Where a contribution citing OASIS v0B fits best:
  - PX4 #29004 (open, unreviewed): the author explicitly disclaims cross-restart replay protection and has not tested power-loss. A comment pointing to OASIS's flash-persisted 128-bit counter window + sender lease, with the real USB power-cut evidence (T8), is directly on point, and the fmu-v2 flash ceiling (99.09 %) is an argument for the small no_std footprint.
  - PX4 #28697/#28698: the shared-replay-table race is a design symptom of signing that binds a timestamp but not the payload per link; OASIS's per-origin counter window and payload-bound preimage are a cleaner comparison point.
  - CIRISServer #402: the open decision is "headers vs signed body" for target/freshness binding. OASIS's domain-separated preimage `"OASIS-MESH-v0B" ‖ network_id ‖ origin_fp ‖ counter ‖ payload_len ‖ SHA-256(payload)` is a worked answer (bind inside the signed preimage, never in headers), and the repo is Rust, so an example is directly reusable.
  - Meshtastic: #12088 shows relays were silently corrupting signed payloads; #11743 (closed) wanted relay budgets and revocation-like behaviour. A docs/discussion contribution on "relay-enforced revocation + hop-mutable fields kept outside the signature (ttl/hops) + payload-digest binding" is the natural fit, but the 256-byte LoRa constraint rules out Ed25519 signatures per packet; OASIS's low-frequency "authority broadcast" guidance should be stated.
  - libmodbus #874 / nanoMODBUS #122 / Victron: these are stack-level bugs and a user-level write-restriction request; the realistic contribution is positioning OASIS's Modbus RTU/TCP gateway (no frame without `Act`) as the "only path to the device" mitigation rather than patching the libraries.
- The ArduPilot 2020 closure ("set up key over a secure channel") and PX4's 2026 CVE show the MAVLink-signing community has accepted timestamp-based anti-replay as sufficient; a factual comparison (timestamp vs persisted counter window) is more persuasive than a critique.

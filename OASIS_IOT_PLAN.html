0. Convention de lecture

Ce document ne vend rien et ne cache rien. Chaque capacité IoT est étiquetée selon ce qu'elle est réellement :

PROUVÉ-HW validé sur matériel réel · SIMULÉ simulation / x86 seulement · STUB squelette, non fonctionnel · THÉÂTRE revendiqué sans preuve · MANQUANT absent

« Compile pour MCU » et « tourne en simulateur (Wokwi/Renode) » ≠ « tourne sur silicium ». Perf x86/WSL sauf mention. Sources : exécution réelle des tests + IOT_READINESS.md (audit 7 dimensions committé).

1. Résumé exécutif (IoT)

Verdict : OASIS est un runtime Rust embarqué pour nœud mesh IoT — crypto réelle, preuves formelles, no_std propre, mesh signé, et désormais calcul d'airtime + throttle duty-cycle. Mais ce n'est pas encore un nœud IoT déployable : le driver radio LoRa est un stub, il n'y a aucune gestion d'énergie, et rien n'a tourné sur silicium réel. Le blocage est matériel, pas logiciel.

no_std RP2040 + STM32F4 444 tests verts 113 preuves Kani 2 Kio Bloom MCU 0 boot silicium 0 ligne énergie

Atouts IoT réels

  • Cœur no_std compile pour Cortex-M0+ (RP2040) et M4F (STM32F4) ; mesh + crypto + porte d'entropie embarquables.
  • Crypto saine : ChaCha20-Poly1305 (vecteur RFC 8439 exact), X25519, Ed25519.
  • Mesh multi-saut signé (v8/v9/v0A) avec dédup Bloom et anti-rejeu (compteur persistant).
  • Airtime LoRa intègre-exact + throttle duty-cycle EU868 (no_std, testé) — conformité réglementaire.
  • Empreinte maîtrisée : Bloom rétréci 64 Kio→2 Kio sur MCU via feature dédiée.

Bloqueurs IoT (sans détour)

  • Driver radio SX1262 = STUB → le lien WAN du nœud n'existe pas sur matériel.
  • Énergie = MANQUANT → nœud sur batterie impossible (100 % CPU, RX permanent).
  • Zéro validation silicium → tout est Wokwi/Renode/x86.
  • Élément sécurisé = STUB → clés en RAM, pas de racine de confiance matérielle.
  • Ed25519 par-saut infaisable sur M0+ (~206 ms/vérif en simulateur).

2. La cible : le nœud IoT OASIS

Produit visé : un nœud embarqué autonome (classe Cortex-M, RP2040/STM32) qui :

  1. communique en mesh LoRa multi-saut signé — résilient, sans cloud, anti-rejeu, insider-résistant ;
  2. exécute un noyau bio-inspiré d'autonomie de bord — porte d'entropie R14 (gel d'actuation si incertitude), réflexes <1 ms, dégradation gracieuse (vitality) ;
  3. tient dans des ressources contraintes — no_std, Bloom 2 Kio, vecteurs zero-alloc ;
  4. porte une identité à racine de confiance — Ed25519 par-nœud, révocation signée par opérateur.

Cas d'usage de niche défendable : capteurs/essaims contraints en environnement sans infrastructure (agriculture, industrie, défense), où ROS 2 est trop lourd et où l'on veut un « système nerveux » déterministe, faible mémoire, à mesh signé résistant au brouillage. Hypothèse à valider sur matériel — non prouvée tant que le silicium n'a pas parlé.

5. Contraintes physiques IoT — chiffrées

Le cœur du dossier : ce que la physique impose à un nœud OASIS réel.

5.1 Airtime LoRa (mesuré, intègre-exact)

Réglage (BW 125 kHz, CR 4/5, CRC)Airtime 24 o
SF7~61,7 ms
SF9~205,8 ms
SF12 (longue portée)~1 482 ms

Référence vérifiée : SF7 / 16 o = 51,456 ms (formule Semtech, octet-exact). Implémenté no_std, sans flottant.

5.2 Duty-cycle réglementaire

EU868 impose 1 % ; émettre au-delà est illégal. OASIS dispose maintenant d'un token bucket airtime (DutyCycleThrottler, preset eu868_1pct) : un driver réel appelle try_send() avant chaque TX et attend si refusé. testé (la moitié logicielle de la conformité ; reste la moitié radio).

5.3 Le mesh à l'échelle se heurte à la radio

La sim « 200 nœuds, ~70 % de couverture » est une sim de topologie, pas de radio. En LoRa réel SF7, 200 nœuds × 2 msg/s ≈ 16,4 s d'airtime par seconde — physiquement impossible. Conséquence produit : un mesh OASIS LoRa doit être petit et bavard avec parcimonie (peu de nœuds, faible débit), ou utiliser des sauts plus rapides/agrégation. À dimensionner avant tout déploiement.

5.4 Coût crypto sur MCU

Opérationx86Cortex-M0+ (Renode)
Ed25519 vérif (mesh v0A)~127 µs~206 ms (~1500×)
Porte R14~331 ns~8 µs

⇒ signature Ed25519 par-saut infaisable sur M0+ : la réserver aux broadcasts d'autorité basse-fréquence ; le mesh courant en v8/v9 (HMAC) pour le trafic fréquent.

5.5 Mémoire dédup (Bloom)

Bloom MCU 2 Kio : ~1 600 insertions avant FPR > 1 % → auto-reset nécessaire (~1 200) sur nœud longue durée (à 1 msg/s ≈ 20 min/cycle). Câblé via OASIS_MESH_AUTO_RESET + avertissement si non configuré.

5.6 Énergie — le trou critique

Aucune gestion d'énergie n'existe (0 hit sleep/WFI/idle/duty/battery). À 1 kHz mesh, la signature v0A seule consomme ~250 mW sur un budget RP2040 ~200 mW ; RX LoRa permanent = pas d'autonomie batterie. Sans cet ajout (Phase 1), « edge IoT sur batterie » est impossible quel que soit le soin du code.

8. Risques IoT — autopsie anticipée

  1. Jamais validé sur silicium/radio (le plus probable) : tout reste sim ; au premier déploiement, timing/RF/brownout/airtime surprennent. Mitigation : Phases 1–2, ~120 $.
  2. Budget énergie ignoré : nœud batterie meurt en heures ; « edge IoT » impossible. Mitigation : idle CPU + RX sur interruption (Phase 1), mesurer.
  3. Mesh sur-dimensionné : ignorer l'airtime LoRa (16,4 s/s à 200 nœuds) → réseau saturé. Mitigation : petits clusters, faible débit, agrégation.

Secondaires : racine de confiance non câblée (clés RAM), crypto non auditée, certif radio absente (illégal d'émettre dehors sans), mono-mainteneur.

9. Recommandation IoT

  1. Une seule tranche, bout-en-bout, sur matériel réel : un nœud capteur LoRa-mesh (driver SX1262 réel → airtime/duty-cycle → mesh signé v9 → mesure énergie). C'est le plus court chemin de « prototype » à « ça marche dehors ».
  2. Ajouter l'énergie dès le premier MCU réel — mesurer, pas supposer.
  3. Câbler la racine de confiance (ATECC608B I2C) avant toute revendication de sécurité.
  4. Dimensionner le mesh sur l'airtime réel, pas sur la sim topologie.
  5. Différer audit crypto + certif jusqu'à une tranche prouvée.

OASIS est un excellent socle embarqué de recherche, livrable en tant que prototype IoT, avec un chemin clair et peu coûteux vers un nœud de niche réel — à condition d'accepter que la prochaine étape décisive soit du matériel, pas du code.

Annexe — Hypothèses IoT à vérifier dans le monde réel

  • Airtime : épinglé sur 1 référence (SF7/16 o = 51,456 ms) ; autres SF/BW dérivés de la même formule (non testés un à un).
  • Perf MCU (Ed25519 206 ms, R14 8 µs) : extrapolée de Renode/Wokwi ; vraies latences (wait-states, IRQ) inconnues avant flash réel.
  • Empreinte RAM/flash : estimée ; le linker MCU réel + co-habitation radio/capteurs peuvent dépasser le budget.
  • Coûts/délais BOM : indicatifs ; à valider (dispo/prix au moment de l'achat).
  • 16,4 s airtime/s : suppose SF7/125 kHz/64 o/2 msg/s — l'ordre de grandeur tient, le chiffre exact dépend des params radio choisis.
